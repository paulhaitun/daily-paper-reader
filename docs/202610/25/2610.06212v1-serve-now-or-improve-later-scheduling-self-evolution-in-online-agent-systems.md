## 摘要
在线智能体可以通过构建可复用的工具、指导信息或模型状态来改善未来服务，但这类工作会与当前请求争用相同的 GPU。利用空闲算力进行自进化面临一个根本性的系统约束：收益只有在产物发布并被使用后才会到来，而暂停进化又会使服务容量等待内存释放和运行时恢复。因此，一项值得完成投资可能也值得推迟。我们提出 LearnSched，一种状态感知调度器，将能力的复用窗口与算力的及时归还纳入统一的投资模型。LearnSched 将候选进度、检查点开销和当前恢复路径纳入动作价值。在相同信息和容量约束下，它使用单步反事实推演，相对于完全计价的窗口策略来选择继续推进、设置检查点或等待。我们通过独立的 A100 组件测量来刻画交接成本，并在 1920 个配对的有限模型场景中评估动作选择。当冷恢复代价高昂时，等待更长的执行窗口可以通过避免交接来提高净价值；在评估的热恢复场景中，强窗口策略已经达到相同价值。保留可恢复状态可以缩短容量归还时间，并降低对复杂进化调度的需求。

## Abstract
Online agents can improve future service by constructing reusable tools, guidance, or model states, but this work competes with current requests for the same GPUs. Exploiting idle compute for self-evolution faces a fundamental systems constraint: benefits arrive only after an artifact is published and used, while pausing evolution leaves service capacity waiting for memory release and runtime recovery. An investment worth completing may therefore be worth postponing. We present LearnSched, a state-aware scheduler that brings the reuse window of a capability and the timely return of compute into a common investment model. LearnSched incorporates candidate progress, checkpoint overhead, and the current recovery path into action values. Under the same information and capacity constraints, it uses one-step counterfactual rollout to choose progress, checkpointing, or waiting relative to a fully costed window policy. We characterize handoff costs through independent A100 component measurements and evaluate action selection in 1920 paired finite-model scenarios. When cold recovery is expensive, waiting for longer execution windows can improve net value by avoiding handoffs; in evaluated warm-recovery scenarios, the strong window policy already achieves the same value. Retaining recoverable state can shorten capacity return and reduce the need for complex evolution scheduling.

## 1. 核心问题与整体含义

**研究动机与背景**

- 在线智能体（如编码 agent）可借助历史轨迹构建**可复用工具、指南或模型状态（如 LoRA 适配器）**，从而在未来减少模型调用、提升回答质量。
- 但这些“自进化”工作与当前用户请求**争用同一批 GPU**，形成根本性矛盾：
  - **收益滞后**：只有产物完成资格验证、发布并被后续请求实际使用后，收益才会到来；
  - **暂停代价**：中断进化并不意味着算力立即归还——需等待显存释放、运行时恢复（冷启动或热恢复），期间服务容量处于“等待”状态。
- 由此提出核心命题：**“一项值得完成的投资，未必值得现在就开始”**（An investment worth completing may therefore be worth postponing）。
- 问题本质是**两个时间尺度的耦合**：前台请求受延迟 deadline 约束；能力构建当下付费、收益分散在未来请求上。

  - **容量悬崖**：静态后台份额从 10% 升至 25%/50% 时，四套系统的 bad request 率显著上升（50% 时均值 37.88%–84.48%）；

## 2. 方法论：LearnSched

### 2.1 核心思想

将在线自进化视为**带延迟回报与状态相关切换成本的算力投资问题**，在**容量归还约束**下，把“能力复用窗口”和“算力及时归还”纳入统一的投资模型，用**单步反事实 rollout** 在“推进 / 存档返回 / 丢弃返回 / 等待”之间选择。

### 2.2 状态与动作建模

- **状态**：\(s_t=(m_t,p_t,\bar p_t,z_t,q_t)\)
  - \(m_t\)：服务或进化模式；
  - \(p_t\)：已完成进度；\(\bar p_t\)：持久化（durable）进度，满足 \(0\le\bar p_t\le p_t\)；
  - \(z_t\)：常驻服务状态及其恢复路径；
  - \(q_t\)：前台积压。
- **动作**：等待、推进工作、检查点并返回、丢弃未保存工作并返回；可行动作集 \(\mathcal A_{\text{ret}}(s,\mathcal I_t)\) 需满足容量归还约束。
- **价值函数**（式 2）：
  \[
  V_t^*(s)=\max_{a\in\mathcal A_{\text{ret}}}\{r(s,a)-c(s,a)+\mathbb E[V^*_{t+\tau}(s')\mid s,a,\mathcal I_t]\}
  \]
  收益在发布并被使用后才计入；成本只计当前动作的执行、检查点、恢复与常驻开销。

### 2.3 关键理论构件

- **有效复用与盈亏平衡**（式 3–4）：固定路径下，需求截止 \(H\)、到达率 \(\lambda\)、使用比例 \(a\)、单位净价值 \(u\)、剩余成本 \(C_e\)，正直接回报要求
  \[
  t<t_e^*=H-\tau_e-\frac{C_e}{\lambda a u}
  \]
  即截止时间必须同时为“完成”和“摊销”预留时间。
- **请求 deadline 与可借容量**（式 6）：基于网络演算的 FIFO 流体队列，对任意 \(k\le i\) 要求
  \[
  B_{ki}\le S_{ki}+R_{ki}
  \]
  即容量损失不得超过基线余量加能力复用节省的工作量；未来收益不增加当前容量。
- **状态相关归还 deadline**（式 7–8）：串行归还路径
  \[
  \tau_r=\tau_{\text{act}}+\tau_{\text{release}}+\tau_{\text{ready}},\qquad t_{\text{reclaim}}\le t_b-\tau_r
  \]
  分别对应命令生效、资源释放、运行时就绪；常驻状态可省去运行时重建。
- **共同定价**（式 9）：\(\Delta U(W)=W\Delta Q_{\text{timely}}-\Delta C_m\)，token、GPU 活跃时间、host 内存分别计量后通过显式价格合并。

### 2.4 调度算法流程

1. **窗口宏动作**（式 10）：已知空闲窗口 \([\ell_k,d_k]\)，动作推进 \(u\) 个时间量子（时长 \(\delta\)），可选检查点，需满足
   \[
   \tau_{\text{load}}+u\delta+\mathbf 1_{\text{save}}\tau_{\text{ckpt}}+\tau_{\text{return}}\le d_k-\ell_k
   \]
   下一窗口从服务模式开始，未保存工作丢弃。
2. **参考策略 Costed Window（\(\pi_0\)）**：对贪心完成计划的全部剩余收益与成本定价，并与“放弃候选、归还容量”比较；优则执行，否则等待并重估。Static ROI 仅从估值中省略交接成本。
3. **单步 rollout**（式 11）：
   \[
   Q_{\pi_0}(s,a)=r(s,a)-c(s,a)+V_{\pi_0}(s'),\qquad \pi_R(s)\in\arg\max_a Q_{\pi_0}(s,a)
   \]
   候选集包含 \(\pi_0(s)\)，平局保留参考动作，每个窗口重算。
4. **Proposition 1（策略改进）**：有限阶段、准确转移/成本/参考值下，
   \[
   V_{\pi_R}(s)\ge V_{\pi_0}(s)
   \]
   证明用阶段归纳；若评分误差满足 \(|\hat Q-Q_{\pi_0}|\le\epsilon\)，仅当 \(\hat Q(s,a)>\hat Q(s,\pi_0)+2\epsilon\) 才替换，可保证真实分数不降。
5. **等待价值**（式 13）：同一产物分别在 \(t_1,t_2\) 发布（\(t_2\ge t_1\)），
   \[
   V_{\text{wait}}-V_{\text{now}}=(C_1-C_2)-g(t_2-t_1)
   \]
   即等待的净收益 = 避免的交接/检查点成本 − 延迟损失的利益。等发布时刻的特例下，等待恰好省去一次检查点与一次归还。
6. **实现复杂度**：枚举 \(O(J)\) 个进度预算、至多 \(K\) 个剩余窗口，对相同持久进度缓存 continuation value；精确 DP 给出该有限动作模型的最优解。

### 2.5 系统实现细节

- **准入估计**：\(w=L_{\max}+0.0625P\)（\(P\) 为 prompt 长度，\(L_{\max}\) 为最大输出长度）；工具预算 1536、指南预算 1024；另有基于 AIMD 的竞争控制器自适应调整后台份额。
- **交接记账**：whole-GPU handoff 会保存 LoRA、终止训练、确认显存释放、启动 serving replica；备选方案保留服务进程并恢复设备状态，以常驻内存换更快恢复。训练从终止后发布的最终持久文件恢复，避免“检查点—发布”竞态。
- **工具发布**：`solve(x)` 需通过 8 个公开输入；每个配置从空库开始。指南生成 base 与 additional 答案，优先选择通过公开测试的 base 答案。请求在派发前冻结可见产物。
- **成本记账**（式 14）：\(C_{\text{all}}=C_{\text{base}}+C_{\text{extra}}+C_{\text{build}}+C_{\text{validate}}\)，失败构建、未发布候选、未使用调用均计费；未知用量记为缺失。
