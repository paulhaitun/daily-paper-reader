Abstract. In high-performance computing (HPC), users must submit resource requirements for their jobs, with user-supplied walltime being a critical parameter. However, these estimates are notoriously inaccurate, as users tend to overestimate walltime to prevent the scheduler from ter-minating their jobs prematurely. While existing work on learning-based walltime prediction primarily focuses on maximizing prediction accu-racy, such predictions are inherently risky for walltime recommendations. Specifically, underestimation leads to job termination before completion, resulting in lost progress and wasted resources. In this study, we present SafeWall, a novel recommendation method that adjusts walltime predic-tions by incorporating an explicit, nonnegative safety buffer to mitigate underestimation risk. The core of our approach is a risk-aware buffer that dynamically calibrates safety margins based on individual user’s histori-cal behavior. When user data is limited, the system employs statistical shrinkage to align these margins with a global baseline, ensuring robust-ness. This yields a lightweight mechanism that optimizes the trade-off between prediction accuracy and termination risk. SafeWall is modular and applicable to various learning-based prediction models. We evaluate SafeWall using five public workload traces, including the full-lifetime job log from the 4,392-node Theta machine at the Argonne Leadership Computing Facility. Across all traces, SafeWall substantially reduces underestimation risk compared to the unbuffered base predictors, while preserving competitive accuracy. The source code is publicly available at 

https://github.com/SPEAR-UIC/JSSPP26-SafeWall .

This mismatch creates a dilemma: an overly large walltime reduces backfilling opportunities, while a small walltime may cause premature job termination, wasting all previously performed computation. Prior work has shown that replacing raw walltime with system-generated runtime information can improve scheduler behavior compared to directly using user-supplied walltime in backfilling settings [20,16,21]. Various runtime prediction techniques have been presented for refining wall-time recommendations, including both classical statistical methods and machine learning-based methods. Batch scheduling imposes a strict penalty for underestimation: if a recommendation is smaller than the actual runtime, the job is terminated; in contrast, a similarly sized overestimate typically only increases reserved slack. Fan et al. This highlights a deployment-facing gap: a state-of-the-art predictor optimized for symmetric loss functions (penaliz-ing under- and over-prediction equally) can yield high prediction accuracy yet fail as walltime recommendations by producing a large fraction of underestimates. In this work, we treat walltime recommendation as a risk-control problem. Specifically, we introduce SafeWall , a two-component design that separates estima-tion from safety. SafeWall first trains a runtime estimator using scheduler-visible features ( base predictor ); it then applies a model-agnostic risk-aware adapter that produces a nonnegative safety margin ( risk-aware buffer ) and outputs a conservative walltime recommendation. This separation is advantageous because it decouples predictive accuracy from risk management: improvements to the base predictor directly translate to better recommendations without redesigning the safety mechanism, while the adapter can enforce explicit underestimation controls independently of the underlying model. As a result, SafeWall is modular, portable across predictors, and robust to changes in workload characteristics. Moreover, the separation makes SafeWall complementary to prior efforts on run-time prediction: any predictor that outputs a runtime estimate can be wrapped with the same buffering logic, allowing existing models to be reused without modification. A key insight that inspired SafeWall is that underestimation risk is heteroge-neous across users. Users exhibit distinct submission patterns and habits; hence, a single global safety margin can be unnecessarily conservative for most jobs while still unsafe for specific users. To address this, SafeWall introduces a user-specific safety buffer: it learns each user’s degree of conservatism from historical data and uses this information to adjust the risk-aware buffer. In cases of cold start and low activity, SafeWall shrinks the risk-aware buffer toward a global baseline, SafeWall: Risk-Aware Walltime Recommendation 3

avoiding unstable or overly aggressive personalization. This yields a continuum between global and personalized risk control, providing stability for cold-start and low-activity users while exploiting user-level structure when sufficient evidence exists. We first evaluate SafeWall using the full-lifetime job log from the 4,392-node Theta machine at the Argonne Leadership Computing Facility [1]. In our experiments, we use XGBoost, a gradient-boosted decision-tree regressor for tabular scheduler logs, as the base predictor due to its strong empirical performance in prior runtime prediction studies [3,15]. We observe that high predictive accuracy does not necessarily translate to a “safe” recommendation; even with a strong regression fit, the base predictor may suffer from a high underestimation rate. By incorporating an explicit nonnegative buffer, SafeWall significantly reduces underestimation risk. As expected, more conservative buffers reduce the underestimation rate at the cost of increased prediction slack. We further evaluate the robustness of SafeWall using multiple public workload traces collected from established repositories, such as the Parallel Workloads Archive [9,13,6,17]. Our results demonstrate that the risk-control layer intro-duced by SafeWall consistently reduces underestimation risk while maintaining prediction accuracy comparable to existing learning-based methods. – We introduce SafeWall, a practical and transparent walltime recommendation design that separates runtime estimation from risk control via an explicit nonnegative buffering layer that can wrap any base predictor ( §3). 

– We evaluate SafeWall using production scheduler logs from multiple systems to assess its robustness across diverse architectures and workloads ( §4).

# 2 Related Work 

Runtime estimates are a core scheduling primitive in HPC batch systems, in-forming decisions such as prioritization, queue management, and backfilling. In practice, however, schedulers typically rely on user-provided walltime limits, which are often discretized and conservative upper bounds rather than accurate runtime predictions. Using these values as if they were true processing times can degrade system performance; yet, replacing them with learned predictions raises an important operational concern: underestimation can be catastrophic because jobs may be terminated at the walltime limit. Fan et al. [8] emphasize that evaluation must therefore go beyond average error and explicitly quan-tify one-sided risk (e.g., the underestimation rate), since improving standard accuracy measures can inadvertently increase termination risk. Related work on underestimation-aware analysis includes an erratum notice associated with a prior 4 K. Xu et al. 

study line on underestimation detection [12], underscoring that measurement and evaluation details matter. A large body of work focuses on improving the base predictor ˆ y by exploring different model families and feature sets. Ensemble learning has been shown to improve predictive accuracy over single models in HPC runtime prediction [5], and transformer-style architectures have been proposed to capture complex nonlinear dependencies in scheduler logs [4]. Another recurring theme is feature availability: although richer application-level signals can improve prediction, they are often difficult to collect and standardize across workloads and systems. Lamar et al. [14] quantify the value of application input parameters, highlighting the potential gains from domain-specific features but also the practical barriers to deploying such approaches broadly in production settings. These results motivate methods that achieve strong performance using scheduler-visible features and lightweight historical summaries. Beyond base prediction, some approaches integrate runtime inference into the scheduling loop. Zrigui et al. [23] propose online job runtime classification to continuously refine processing-time information used by the scheduler, demon-strating that classification-oriented runtime information can improve scheduling outcomes compared to naively using loose walltime requests. In parallel, several systems incorporate conservative margins or post-processing rules into walltime recommendations to mitigate harmful underprediction. Oztop et al. [18] propose a job grouping framework that clusters similar jobs before prediction and discuss conservative strategies to reduce underestimation risk, reinforcing the view that post-processing policies can remain valuable even when base predictors are strong. Similarly, Cui et al. [7] target backfilling with a classification-oriented pipeline and conservative recommendations to reduce operational underprediction. Finally, the realism of evaluation depends on trace fidelity and label quality: “runtime” recorded in logs may include artifacts (e.g., measurement granularity, truncation, or missing/censored outcomes). Klus´ aˇ cek and Chlumsk´ y [13] introduce a real-life workload trace with refined runtime estimates and show that improving labels can materially change conclusions about prediction and scheduling policies. This highlights an important practical consideration for many studies: even strong models can be shaped by the quality and semantics of the available runtime labels. 

The novelty of SafeWall lies in its separation of prediction from recommen-dation. While prior work focuses primarily on maximizing accuracy through advanced models or richer feature sets, SafeWall introduces an explicit risk-control layer atop any base predictor. By decoupling runtime estimation from recommendation via a model-agnostic, nonnegative buffer that adapts to indi-vidual historical behaviors, SafeWall remains orthogonal to existing research. It serves as a complementary framework that enhances, rather than replaces, traditional walltime prediction studies. SafeWall: Risk-Aware Walltime Recommendation 5

# 3 Methodology 

HPC clusters typically use batch schedulers in which users submit jobs and the scheduler decides when and where they run; each job is submitted with a walltime limit specifying its maximum allowed runtime. The objective of SafeWall is twofold: (i) to accurately estimate a job’s actual execution time, and (ii) to recommend a conservatively buffered walltime that minimizes the risk of premature termination. As shown in Figure 1, SafeWall adopts a two-component design. First, a learning-based runtime estimator produces a runtime estimate from scheduler-visible features. Second, a model-agnostic risk-aware adapter computes a non-negative adjustment value (i.e., buffer) from historical prediction outcomes and outputs the recommended walltime. SafeWall first trains a base predictor on scheduler-visible features (and lightweight user-history summaries when available) to produce ˆ y. It then calibrates a buffer from training residuals e = y − ˆy and ap-plies a nonnegative adjustment b—globally or in a risk-aware, shrinkage-stabilized manner—to form the final recommendation ˜ y = ˆ y + b.Because this buffering step is applied after prediction and is calibrated using past prediction errors, it is compatible with the various runtime predictors described in Section 2 (e.g., ensembles or transformer-based models). This makes SafeWall complementary to existing efforts that focus solely on improving the base predictor accuracy. Formally, let i ∈ { 1, . . . , n } index the jobs. Each job is associated with a feature vector xi ∈ Rd available at submission time (where d is the number of features), an observed runtime yi ∈ R≥0 (seconds), and a user identifier ui used for optional risk-aware buffering. SafeWall learns a prediction function f (·) that produces a runtime estimate ˆyi = f (xi), (1) and then applies a nonnegative safety buffer to convert this estimate into a conservative walltime recommendation: ˜yi = ˆ yi + bi, bi ≥ 0. 3.2 Feature Engineering 

Next, prior to applying any prediction method, we must develop a robust feature representation to capture the essential temporal and structural characteristics of the workload. We compute per-user lag features from prior completed jobs (previous run-time, second previous runtime, and their mean), along with summary statistics capturing request accuracy and runtime scale. For each prior job j, we define request accuracy as 

aj = min(wall j /y j , y j /wall j ) ∈ (0 , 1] ,

and include per-user summaries (mean/max) and recent-history variants over the last 10 completed jobs when available. We also include longer-run runtime summaries (mean/max, recent mean/max, and the 25th percentile of prior successful runtime) [8,22]. All history features are computed strictly from jobs submitted earlier than the current job, preventing information leakage. 

Missing values and cold-start users. User-history features are undefined for users with insufficient prior completed jobs. Rather than dropping these jobs or imputing missing history, we treat them as cold-start cases and fall back to the user-provided walltime request as the recommendation. This conservative fallback avoids unsafe recommendations when there is not enough evidence to support history-based personalization. After filtering, the dataset contains 430,223 jobs; 367,477 jobs have sufficient history for the full feature set and are used for model training and evaluation, while 62,746 jobs use the walltime fallback. Because batch schedulers enforce a submission-time walltime limit and may terminate jobs when that limit is reached, user-submitted walltime provides a safe default when history features are unavailable [19].

3.4 Risk-Aware Buffer Adapter 

A base prediction ˆ yi may achieve excellent accuracy while still being operationally risky for batch scheduling due to asymmetric costs: an underestimate can termi-nate a job at the walltime limit, whereas an overestimate typically results only in reserved slack.

The design begins with a globally calibrated error buffer and then applies a user-adjusted tweak when historical evidence supports personalization. This keeps the mechanism simple and auditable while explicitly targeting the one-sided underprediction tail that drives termination risk. Specifically, SafeWall proceeds in three steps as detailed below. 

Step 1: global error buffer from training residuals. We begin by calibrating a single global adjustment value using the model’s historical underprediction errors. After training the point predictor, we run it on the training set and record the residual for each job, 

ei = yi − ˆyi,

which measures how far the prediction is below (or above) the realized runtime. Positive residuals ( ei > 0) are precisely the cases that matter for termination risk: they correspond to jobs whose true runtime exceeded the point estimate. To translate these historical underprediction errors into a conservative shift, we choose a target underestimation rate τ ∈ (0 , 1) (e.g., τ = 0 .10). Intuitively, 

τ specifies the fraction of future jobs we are willing to allow to still exceed the recommended walltime after buffering. We then set the global adjustment value 

bg(τ ) to a high quantile of the positive residual distribution: 

bg(τ ) = Q1−τ ({ ei : ei > 0, i ∈ I train }) . (8) 10 K. Xu et al. 

This choice has a direct interpretation. Consider all training jobs for which the model underpredicted. By construction, bg(τ ) is large enough to cover approxi-mately a (1 −τ ) fraction of those historical underpredictions; that is, for most past underpredicted jobs, ˆ yi + bg(τ ) would have met or exceeded yi. When training and test conditions are similar, applying the same adjustment on new jobs aims to keep the empirical underestimation rate near τ , while exposing a clear knob that trades lower UR for higher reserved slack. 

Step 2: user-adjusted tweak with shrinkage. A single global adjustment value is an average-case policy. In practice, residual behavior can be heterogeneous across users: some users routinely run longer than the model predicts (large positive residuals), while others are typically well covered by the point predictor or even overpredicted. To reflect this heterogeneity, we estimate a risk-aware adjustment value from each user’s historical underprediction residuals, and then stabilize it using shrinkage. For each user u, let Eu = { ei : ei > 0, u i = u, i ∈ I train } denote the set of that user’s positive training residuals, and let nu = |E u| be the number of usable underprediction cases. 4.4 Analyzing the Impact of Risk-Aware Buffering 

Prediction errors are not uniformly distributed across users. Among “stable” test users (those with at least 10 jobs), 35.8% exhibit a positive mean residual (sys-tematic under-prediction) and 64.2% exhibit a negative mean residual (systematic over-prediction). Moreover, user mean-residual bias shows persistence from train to test (Pearson correlation 0.167 among stable users). This empirical heterogene-ity motivates risk-aware buffering: a single global margin is an average-case policy that can remain unsafe for some users while being unnecessarily conservative for others. 

# 5 Discussion 

SafeWall is motivated by a practical mismatch between how runtime predictors are typically trained and how their outputs are used as walltime limits in batch scheduling. Our results suggest that explicitly separating estimation (predict ˆ y)from risk control (add a nonnegative margin b) is an effective way to convert strong base predictions into scheduler-safe recommendations. Below, we summarize the main strengths, limitations, and implications for deployment. 

5.1 Strengths 

SafeWall’s main strength is its modular two-component design . The buffer adapter relies only on historical residuals and can wrap any base predictor, including future models with richer features, without altering the safety logic. Improvements in prediction quality directly benefit, while the risk-aware buffering layer provides a separate, auditable mechanism for controlling underestimation risk. From an operational standpoint, SafeWall is simple and tunable . A single parameter (e.g., a target underestimation rate or residual percentile) directly controls the trade-off between recommendation tightness and slack. Because buffering is applied post-training, SafeWall remains model-agnostic , allowing for straightforward validation and deployment. Moreover, risk-aware buffers offer a practical balance between global and personalized policies: it adapts to individual user behaviors when historical data are abundant, while employing shrinkage toward a global baseline to mitigate instability in data-sparse or cold-start scenarios. 

5.2 Limitations 

SafeWall’s calibration depends on the semantics and quality of runtime labels. In real scheduler logs, jobs that reach their requested walltime are right-censored: the recorded runtime reflects the walltime limit rather than the job’s true completion time. If such walltime hits are common, then residuals computed from observed runtimes can understate the positive tail (i.e., the most harmful underpredictions), which may lead to buffers that are not conservative enough. In these settings, 18 K. Xu et al. 

censored records should be handled explicitly during calibration. Two practical options are: (i) treat walltime-hit jobs as incomplete observations and incorporate them as conservative lower bounds when estimating tail residuals (so the buffer does not rely on artificially capped runtimes), or (ii) leverage refined-runtime or soft-walltime traces that reconstruct more accurate runtimes for censored jobs and thus provide cleaner residual signals for buffer estimation [13]. SafeWall assumes residual behavior is reasonably stable between calibration and use. Significant shifts in workload composition, software environments, or scheduling policies can alter residual distributions and degrade calibration ac-curacy. While rolling-window updates can mitigate such drift, they introduce additional hyperparameter tuning requirements. Finally, personalization may introduce unequal service levels , as harder-to-predict users receive larger buffers. Depending on site policy, group-based buffering policies (per partition, project, or job class) may be appropriate to ensure equitable resource access. 

# 6 Conclusion 

This work addressed the practical gap between accurate runtime prediction 

and safe walltime recommendation in batch-scheduled HPC systems. Using the 6.5-year Theta log, we showed that even strong symmetric predictors can yield unacceptably high underestimation rates under hard walltime limits. To address this, we introduced SafeWall, a two-component approach that separates estimation from risk control by augmenting a base predictor with a model-agnostic, risk-aware buffering layer that explicitly manages one-sided termination risk. Experiments on the Theta trace and multiple public datasets demonstrate that SafeWall outperforms existing methods by offering a well-defined accuracy-risk trade-off; specifically, its residual-calibrated buffers provide predictable operating points, while the risk-aware buffering achieves lower underestimation rates than global or prior conservative approaches without introducing unnecessary slack. Overall, the results support treating walltime recommendation as an explicit risk-control problem. SafeWall provides a modular framework that complements existing runtime prediction models. As a lightweight solution relying solely on submission-time features and historical data, it can be deployed as either a standalone recommen-dation service or a submission-time wrapper that automatically adjusts walltime requests. The source code is publicly available at https://github.com/SPEAR -UIC/JSSPP26-SafeWall .Future work includes making calibration conditional on job attributes (e.g., queue/partition, node count, or project) so the buffer adapts to systematic heterogeneity beyond users, and integrating SafeWall into a scheduler workflow to evaluate system-level impacts such as backfilling efficiency, utilization, and wait time. We also plan to handle right-censored jobs explicitly in environments where walltime hits are frequent, and to pair SafeWall with uncertainty-aware SafeWall: Risk-Aware Walltime Recommendation 19 

base predictors (e.g., quantile or conformal calibration) to strengthen reliability while preserving the same modular two-component design.
