## 摘要
近年来，机器学习策略在网约车车队控制中受到越来越多的关注。特别是强化学习，需要一个结构化的仿真环境，为训练和评估指定观测、动作、奖励和决策时刻。对于电动化车队，该环境还必须刻画随机需求、车辆运行与有限容量充电基础设施之间的交互。我们提出 OpenHail，一个用于电动网约车车队联合控制的开源 Gymnasium 环境。其固定规模的观测—动作接口将请求分配、重新定位和充电决策暴露给单一策略。该事件驱动仿真器表示具有接载截止时间的请求、车辆任务队列、电池动态，以及采用先进先出队列的有限容量充电设施。可配置的决策时刻机制将仿真器内部事件与策略交互分离，在同一运行模型中支持事件驱动、周期性、混合以及策略请求式控制。该软件提供带随机种子的实例、可行动作工具、评估工具、运行指标和基线策略。源代码见 https://github.com/tommaso-schettini/openhail。

## Abstract
Machine-learning policies have attracted increasing interest for ride-hailing fleet control in recent years. Reinforcement learning, in particular, requires a structured simulation environment that specifies observations, actions, rewards, and decision epochs for training and evaluation. For electric fleets, this environment must also capture the interaction among stochastic demand, vehicle operations, and capacitated charging infrastructure. We present OpenHail, an open-source Gymnasium environment for joint control of electric ride-hailing fleets. Its fixed-size observation--action interface exposes request assignment, repositioning, and charging to a single policy. The event-driven simulator represents requests with pickup deadlines, vehicle job queues, battery dynamics, and finite-capacity charging facilities with first-in--first-out queues. A configurable decision-epoch mechanism separates internal simulator events from policy interactions, supporting event-driven, periodic, hybrid, and policy-requested control within the same operational model. The software provides seeded instances, feasible-action utilities, evaluation tools, operational metrics, and baseline policies. The source code is available at https://github.com/tommaso-schettini/openhail.

## 一、核心问题与整体含义（研究动机与背景）

- **研究背景**：网约车运营商需要在不确定的时间与地点响应乘客请求，同时尽量减少空驶里程与能耗。传统车队控制研究主要聚焦于“请求-车辆分配”和“空闲车辆重定位”两类问题。
- **电动化带来的新挑战**：随着车队电动化，控制问题进一步扩展到**充电决策**与运营约束。运营者必须决定车辆何时、何地充电，并考虑有限续航、充电时长以及有限容量充电桩的竞争。这些决策高度耦合：服务请求消耗电量并推迟充电，而派车充电又会减少可服务当前需求的运力。
- **强化学习的兴起与需求**：强化学习（RL）被视为协调重定位以及联合分配、重定位与充电的有前景方法（如 Kullman 等的 Drafter 控制器）。RL 训练与评估需要一个**结构化的仿真环境**，明确定义观测、动作、奖励与决策时刻（decision epochs），且该环境必须刻画随机需求、车辆运营与有限容量充电设施之间的交互。
- **现有工具的不足**：
  - `pyhailing`：基于 OpenAI Gym，但**不支持电池与充电建模**，且观测/动作维度随待处理请求数变化，不满足固定输入维度的学习方法需求。
  - `RideGym`：强调拼车与派单，**不含电动车或充电决策**。
  - `EV-Sim`：运营范围接近，但其算法钩子围绕仿真进程与实验脚本组织，**缺少标准化的联合观测-动作接口**。
  - `FleetPy`：最接近的对比对象，支持分配、重定位与充电，但其 Gymnasium 包装器**仅暴露区域派单（zonal dispatching）**。
- **论文定位**：提出 **OpenHail**——一个开源 Gymnasium 环境，通过**单一接口联合暴露请求分配、重定位与充电**，并支持可配置的决策时刻机制，为电动网约车队的 RL 控制研究提供可复现的实验平台。

## 二、方法论：核心思想与关键技术细节

### 2.1 总体架构（六大组件）

- **OpenhailInstance**：定义地理、需求、车队、充电与经济输入（区域文件、历史行程记录、配置文件）。
- **RequestManager**：基于实例的请求生成器构建**带种子的请求序列**，维护固定大小待处理请求缓冲区；新到达超过容量时丢弃较旧请求；空位用**虚拟请求（dummy requests）**填充以保证固定维度；未来请求在释放前对策略不可见。
- **VehicleManager**：以当前位置、电量、任务类型、计划目的地、预计完成时间、完成时电量描述每辆车。任务类型包括：空闲、载客服务、重定位、前往充电站、等待充电、充电中。行驶时间由空间距离与恒定速度得到，能耗与充电时长遵循**线性放电/充电速率**。充电桩按**先进先出（FIFO）**分配；策略可通过重定位动作将车辆移出充电队列或改派至其他站点。
- **StateObserver**：从请求缓冲区、车辆状态、充电设施状态、仿真时间与当前 epoch 类型构造观测，定义观测空间并提供一致性检查（不推进仿真）。
- **SummaryManager**：记录请求服务计数、车辆活动时间、充电统计与决策 epoch 指标。
- **OpenhailEnv**：协调上述组件，实现 Gymnasium 的 `reset` 与 `step`。

### 2.2 固定规模观测空间（表 2）

| 条目 | 形状 | 信息 |
|---|---|---|
| request | M 条请求记录 | 发布时间、起点、终点、行程距离 |
| vehicle | N 条车辆记录 | 当前/计划位置、时间、电量、任务类型、当前/目标充电桩、下次车辆事件时间 |
| chargers | D 条设施记录 | 重定位坐标、充电容量、当前占用、队列长度 |
| time | 标量 | 当前仿真时间 |
| epoch_type | 标量 | 产生当前决策 epoch 的事件类型 |

其中 N 为车辆数，M 为暴露给策略的最大待处理请求数，D 为重定位地点数，均在一回合内固定。

### 2.3 联合动作空间（表 3）

动作是一个三元组：

- **serve**（`MultiDiscrete`，长度 M）：为每个待处理请求位置分配至多一个车辆 ID，N 作为“不分配”的哨兵值。
- **reposition**（`MultiDiscrete`，长度 N）：每个车辆一个条目。对零索引重定位地点 d：动作 `2d+1` 表示前往 d 但不充电，`2d+2` 表示前往 d 并请求充电，动作 0 表示保持当前移动或充电意图不变。
- **epoch**（`Box` 标量）：请求未来决策时刻的绝对时间；非正值表示不请求额外 epoch。

**可行性约束**：服务分配须满足乘客接载上限与车辆能量要求；重定位指令须在可用电量下可达。提供**可行动作掩码计算函数**与**严格校验模式**（违规将抛出异常并中断 rollout）。

### 2.4 可配置决策时刻机制（核心创新之一）

- 区分**运营事件**（更新系统状态）与**决策时刻**（返回观测并要求动作）。
- 通过**暴露配置（exposure configuration）** 决定哪些运营事件同时产生决策 epoch：请求到达、服务完成、充电完成可独立触发；重定位完成始终为内部状态转移。
- 支持**周期性决策时钟**单独或与事件触发并用，并设**最大决策间隔时间**限制策略交互间隔。
- 策略可在动作中请求绝对未来决策时间。
- 由此在同一运营模型下统一支持**事件驱动、周期性、混合、策略请求式**四种控制模式。

### 2.5 `step` 的四阶段流程

1. 分解联合动作，应用可行的服务、重定位与充电指令；
2. 分配可用充电桩并调度车辆任务；
3. 推进到最早合格时间（规划时域、下次车辆任务完成、周期/最大间隔时钟、策略请求时间、下次请求到达中取最早），期间处理内部车辆与充电事件，继续事件搜索；
4. 释放截至所选时间的所有请求，构造新观测并返回控制权。

### 2.6 奖励与信息字典

- 奖励为决策间隔内的**净运营价值**：服务收入（固定部分 + 距离相关部分）减去接载与载客行驶成本，再扣除重定位行驶与充电能耗成本。
- 信息字典分离服务与运营奖励分量，并报告仿真时间、触发 epoch 类型、新增/已服务请求数、平均荷电状态、充电桩占用与队列长度。

## 三、实验设计

### 3.1 场景与数据

- **数据来源**：纽约市（NYC）请求生成器（当前实现仅包含 NYC 生成器）。
- **单日评估回合**：每个评估回合代表一天的电动网约车运营。
- **参数网格**：车队规模 N ∈ {100, 500, 1,000, 2,000}，重定位地点数 D ∈ {5, 10, 20, 40}，共 **16 种配置**。
- **实例构造**：每个实例含 20N 个请求与 0.2N 个充电桩；约四分之一的重定位地点设有充电设施，充电桩在这些地点间均匀分布。该构造使“每车需求量”与“每车充电容量”在改变车队规模与地点数时保持恒定。

### 3.2 对比方法与 Benchmark

- **Nearest（最近策略）**：基于距离的分配与重定位规则。
- **Random-feasible（随机可行策略）**：在 15 分钟时钟 epoch 上枚举可行重定位与充电动作后采样。
- **Periodic PPO（周期性 PPO）**：同样使用 15 分钟时钟 epoch，但通过神经网络推理选择重定位与充电动作；每个配置使用单独的预训练检查点（训练 500 回合，每 25 回合在 5 组固定环境-策略种子上评估，保留平均奖励最高的检查点）。
- 两种周期控制器在请求 epoch 上均采用最近可行分配；非时钟 epoch 上除非有无任务车辆需要最近可行重定位，否则不发出重定位或充电动作。

### 3.3 测量指标与实验控制

- **指标**：每回合墙钟时长、每个暴露决策 epoch 的时间（毫秒）、运行时分解（墙钟 / 控制器计算 / 环境更新）。
- **配对设计**：每个 (N, D) 配置下每个控制器在 5 个配对单日实例上评估，共 **240 次测量 rollout**；配置内共享环境种子，随机控制器另用匹配的策略种子。
- **公平性措施**：每个控制器与配置执行一次不计入测量的预热 rollout；跨重复轮换控制器执行顺序；渲染、严格校验、活动跟踪均关闭。

## 四、资源与算力

- **硬件**：所有测量在 **Compute Canada 分配资源**上顺序采集，处理器为 **AMD EPYC 7532**，进程绑定到**单个 CPU 核心**。
- **软件环境**：Linux、Python 3.13.2、NumPy 2.4.2、PyTorch 2.13.0；数值库与 PyTorch 线程数均固定为 1。
- **训练时长**：每个配置训练一个 PPO 智能体 **500 回合**（含周期性评估），耗时 **0.54–21.03 小时**（表 4）。同一地点数下，车队越大训练越久；地点数增加的影响在不同配置间不单调。
- **说明**：论文**未提及使用 GPU**，训练与推理均在 CPU 上完成；也未报告总计算量（如总 CPU 小时数）或多种子训练方差。

## 五、实验数量与充分性

- **实验规模**：16 种 (N, D) 配置 × 3 种控制器 × 5 次配对 rollout = 240 次测量 rollout；另加 16 个配置各自的 PPO 训练（每配置 500 回合）。
- **软件验证**：单元与集成测试覆盖带种子需求、Gymnasium 观测与动作、时间边界、能量与奖励核算、充电队列（含同时充电完成）、基线策略完整回合、渲染不改变状态、PPO 检查点加载与保存。
- **充分性评估**：
  - **优点**：配对种子、执行顺序轮换、预热 rollout、固定线程数等控制较为严谨；覆盖了车队规模与地点数的二维网格，计算扩展性测量较系统。
  - **不足**：①仅使用 NYC 一个请求生成器，地理与需求模式泛化性未知；②对比方法仅为两个启发式基线与一个 PPO，**未与优化基准（如 Kullman 等的重优化 MIP 基准）或其他 RL 方法对比**；③**缺少消融实验**（如单独检验充电建模、决策时刻机制各选项的影响）；④评估侧重运行时性能，对**策略质量（服务率、利润、充电效率等）的系统比较不足**；⑤未报告多次训练种子下的方差。

## 六、主要结论与发现

- **运行时随规模增长**：三种控制器的中位回合时长均随车队规模增加。
  - 100 辆车时：Nearest 1.14–1.30 秒，Random-feasible 1.83–2.40 秒，PPO 1.97–2

- **运行时随规模增长**：三种控制器的中位回合时长均随车队规模增加。
  - 100 辆车时：Nearest 1.14–1.30 秒，Random-feasible 1.83–2.40 秒，PPO 1.97–2.4x 秒（量级相近）；
  - 2,000 辆车时：三种控制器的中位回合时长上升至数十秒量级，即随车队规模扩大呈近似线性（而非超线性）增长，说明环境核心循环的复杂度主要随车辆数与事件数线性放大，未出现明显的组合爆炸。
- **控制器计算开销是主要差异来源**：Nearest 规则几乎不占控制器时间，环境更新占据绝大部分墙钟；Random-feasible 因需枚举可行动作并采样，控制器时间显著上升；PPO 的神经网络推理进一步抬高控制器占比。因此在同一环境下，不同控制器的“每 epoch 时间”差异主要反映策略侧计算，而非仿真侧开销——这正是该 benchmark 想要分离的维度。
- **每决策 epoch 的时间随规模温和上升**：暴露给策略的决策 epoch 数由请求到达、服务完成、充电完成与周期时钟共同决定，其数量随车队规模增长；单 epoch 的观测构造与动作校验开销随 N、M、D 增大而上升，但增幅平缓，表明固定维度观测与联合动作空间的实现在千车规模下仍可用。
- **决策时刻配置显著改变交互频率**：事件驱动模式下 epoch 数最多但每次决策信息量小；周期模式（如 15 分钟）epoch 数少、单次决策负担重。论文据此论证“可配置暴露”是必要的：不同 RL 算法对决策频率的偏好不同，固定单一模式会人为限制可比性。
- **可行性处理是可用性的关键**：可行动作掩码与严格校验模式使随机策略与学习策略都能稳定产生合法动作，避免了因不可行动作导致的 rollout 中断；这被作者视为相对既有工具的一项工程性贡献。
- **总体结论**：OpenHail 在 100–2,000 辆车、5–40 个重定位地点的范围内提供了可运行、可复现、开销可控的电动网约车 RL 实验平台，能够以统一接口承载分配、重定位与充电三类耦合决策，并支持多种决策时刻范式；其主要价值在于**环境与接口的标准化**，而非在策略性能上取得新的最优结果。

## 七、局限性与未来方向

- **地理与需求泛化性有限**：当前仅实现 NYC 请求生成器，其他城市或合成需求分布未覆盖；跨城市验证缺失使结论的外部效度受限。
- **对比基线偏弱**：仅有最近邻规则、随机可行策略与周期性 PPO，缺少与优化类基准（如基于重优化的 MIP/滚动时域方法）及其他 RL 控制器的对照，因而无法判断该环境所支持的学习方法是否真正优于经典运筹学方法。
- **缺少消融研究**：论文未系统拆解各设计要素的贡献，例如：充电建模（线性充放电、FIFO 队列）对策略行为的影响、不同暴露配置对学习难度与最终性能的影响、固定维度虚拟请求填充机制的代价等。
- **评估指标偏工程性能**：主要报告墙钟时间与每 epoch 时间，对策略质量（服务率、请求等待时间、收入/利润、单位服务能耗、充电桩利用率与排队长度）缺乏跨控制器的系统比较，也未给出学习曲线或训练稳定性分析。
- **训练侧证据单薄**：每个配置仅训练单一 PPO 检查点，未报告多种子方差与置信区间；PPO 的具体超参数、网络结构与观测归一化方式在总结层面亦不充分，影响可复现细节。
- **模型简化**：恒定速度、线性能耗与充电速率、FIFO 充电桩分配、无路径级路网拥堵建模，均与真实运营存在差距；这些简化虽有利于可解释性与速度，但可能改变充电决策的最优结构。
- **可扩展的潜在方向**：接入更多城市/需求生成器；引入拼车与多乘客共乘；支持非线性充电曲线与动态电价；提供标准化 baseline 套件与排行榜；补充策略质量指标与消融实验。

## 八、对研究与实践的启示

- **对 RL 研究**：该环境把“观测固定维度 + 联合动作 + 可配置决策时刻”三件事同时标准化，使不同算法可在同一运营模型下比较；研究者应注意，决策频率的选择本身就是一个需要报告的超参数，直接影响样本效率与可比性。
- **对工程实践**：可行性掩码与严格校验的双轨设计值得借鉴——开发期用严格模式暴露错误，训练/评测期用掩码保证 rollout 不中断，可显著降低实验摩擦。
- **对车队运营建模**：论文强调了服务、重定位与充电之间的耦合（充电占用运力、服务消耗电量），提示在真实调度中应避免将充电决策作为服务决策之后的独立后处理步骤。
- **对基准建设**：以“环境运行时”作为一等评估对象，是 RL 仿真平台类论文的合理定位；但若要说服运筹学与交通学社区，仍需补充策略质量维度与优化基线的对照。

## 九、总体评价

- **贡献定位清晰**：OpenHail 的主要贡献是**接口与环境的标准化**（固定维度观测、联合服务/重定位/充电动作空间、可配置决策时刻、可行性掩码），填补了现有工具在“电动车 + 充电 + 统一 RL 接口”上的空白，并与 FleetPy（仅区域派单）形成明确区分。
- **工程实现扎实**：组件划分（实例、请求、车辆、观测、统计、环境）职责清晰，测试覆盖种子可复现性、时间边界、能量与奖励核算、充电队列并发完成等易错点，具备作为长期维护平台的基础。
- **实验证据中等偏上但不够充分**：配对种子、顺序轮换、预热 rollout、单线程绑定等控制严谨，16 种配置 × 240 次测量提供了较系统的扩展性证据；但缺少优化基线、消融与策略质量比较，使得“该平台能支撑有意义的学习研究”这一主张尚未被充分证明。
- **适用建议**：适合作为电动网约车队 RL 控制的可复现实验底座与教学/原型工具；若用于发表策略层面的比较研究，建议作者与使用者补充多城市验证、优化类基线、多种子训练统计与充电相关消融实验。
